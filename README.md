# smd-component-finder

Инструмент идентификации SMD-компонентов по маркировке, номеру детали или снимку с камеры.

Два движка: **поиск по маркировке** (нечёткий, полностью в браузере) и **поиск по
даташитам** (RAG по локальной библиотеке PDF, поднимается одним скриптом).
Всё локально: ничего не уходит на сервер.

> **Интерфейс — на английском** (так удобнее для общедоступного инструмента);
> этот README и комментарии в Python-инструментах — на русском.

Репозиторий появился как результат разбора эталонного инструмента
[smtinsider.com/finder](https://www.smtinsider.com/finder). Разбор — в **[ANALYSIS.md](ANALYSIS.md)**:
что там сделано хорошо, какие узкие места и что именно переделано здесь.

## Быстрый старт

Открыть локально (без сборки и зависимостей):

```bash
# статический сервер без RAG (поиск по маркировке работает, панель даташитов — нет)
python3 -m http.server 8000

# полный вариант: сайт + /api/* на одном origin
python3 tools/rag/serve.py --port 8000
# затем http://localhost:8000
```

Сборка не требуется. Поиск по маркировке работает и при открытии `index.html`
напрямую с диска, а вот камера и `/api/*` потребуют `https://` или `localhost` —
это ограничение браузера, а не кода.

## Веб-парсер: скармливаем папку с PDF

Самый короткий путь «папка с PDF → SQLite → карточки на сайте» — без командной
строки. Запустите сервер, откройте страницу и найдите блок **1 · Load your PDFs**
(первый на странице).

| Что нажать | Что произойдёт |
|---|---|
| **Folder path** → путь до папки → **Parse folder** | сервер сам обойдёт папку (переключатель *Subfolders* — с подпапками или нет), найдёт все `*.pdf` и распарсит их |
| **Choose folder** → папка в браузере → **Upload & parse** | файлы уедут на сервер в `data/datasheets/uploaded/<дата-время>/` и сразу попадут в разбор |
| **Stop** | остановит текущий прогон; уже записанное останется в базе |

Во время работы виден прогресс: `сделано / всего`, скорость (PDF/с), оценка
времени до конца и список файлов, которые не разобрались, — с причиной по
каждому. Как только прогон заканчивается, сетка карточек и фильтры обновляются
сами: перезагружать страницу не нужно.

Поведение, которое важно на больших объёмах:

* **Докачка.** Уже разобранные файлы запоминаются по SHA1, поэтому повторный
  запуск по той же папке не пересчитывает ничего (`skipped`). Если файл
  разобрался, но карточка от этого не стала полнее — это `unchanged`.
* **Один битый PDF не роняет прогон.** Он попадает в список ошибок и в таблицу
  `failures`, остальные продолжают считаться.
* **Парallel.** Разбор идёт в пуле процессов (`--jobs N`), сайт при этом
  продолжает отвечать: карточки видны по мере готовности.

То же самое с командной строкой (например, на сервере без браузера):

```bash
python3 tools/rag/serve.py --port 8000 --jobs 8

curl -X POST -H "Content-Type: application/json" \
     -d '{"path":"/home/user/datasheets","recursive":true}' \
     http://localhost:8000/api/ingest/path
# → {"job_id": "1a2b3c4d5e", "files": 300000, "folder": "/home/user/datasheets"}

curl "http://localhost:8000/api/ingest/status?id=1a2b3c4d5e"   # прогресс
curl -X POST -H "Content-Type: application/json" \
     -d '{"id":"1a2b3c4d5e"}' http://localhost:8000/api/ingest/cancel
```

Базу можно держать вне репозитория — пригодится, когда карточек станет много:

```bash
SMD_DATA_DIR=/mnt/big-disk/smd python3 tools/rag/serve.py --port 8000
```

## Архитектура: Docling + OpenSearch

Два решения, каждое из которых закрывает свою поломку.

### Docling вместо текстового парсинга

`pdfplumber` угадывает границы ячеек по линиям и позициям символов. Там, где
в даташите нет вертикальных линеек — а их обычно нет, — распиновка диода
превращается в одну колонку вида `1 Base Control input`, а параметры корпуса
(Pitch, Lead Width) слипаются в строку. **Docling** сначала прогоняет модель
разметки страницы, потом TableFormer по найденным табличным областям, и
границы ячеек восстанавливаются по содержимому, а не по линейкам.

Стоимость этого качества — модели. Полный Docling на каждой странице это
секунды на страницу на CPU: на 300 тысячах даташитов (миллионы страниц) одна
машина такое не вытянет вообще. Поэтому парсер работает **маршрутизацией**:

```
PDF -> дешёвый проход pdfplumber (текст всех страниц + где есть таблицы)
    -> Docling только на страницах с таблицами (обычно 10–20 % документа)
    -> таблицы Docling заменяют таблицы pdfplumber на этих страницах
```

Именно таблицы — то, ради чего нужен Docling: весь остальной текст и так
достаётся текстовым слоем без всяких моделей.

```bash
# так по умолчанию
python3 tools/rag/pipeline.py --rebuild --docling-pages tables
# полное качество на отдельной партии (медленно, но максимально точно)
python3 tools/rag/pipeline.py --rebuild --docling-pages all
```

Настройки Docling (переменные окружения):

| Переменная | Смысл |
|---|---|
| `SMD_DOCLING_PAGES` | `tables` (по умолчанию) или `all` |
| `SMD_DOCLING_TABLE_MODE` | `fast` (по умолчанию) или `accurate` — TableFormer |
| `SMD_DOCLING_DEVICE` | `auto` / `cpu` / `cuda` |
| `SMD_DOCLING_THREADS` | потоков на процесс (по умолчанию 2: мы параллелим процессами) |
| `DOCLING_ARTIFACTS_PATH` | где лежат веса — для машин без интернета |

Конвертер создаётся **один раз на рабочий процесс**, а не на файл: загрузка
весов — самая дорогая операция, и повторять её 300 тысяч раз нельзя.

### OpenSearch вместо «только FTS5»

Поиск по библиотеке компонентов — это два разных вопроса, и один движок на
оба не годится:

* **Точная строка.** Маркировка `KL1`, парт-номер `BAT54`, корпус `SOT-23-5`.
  Векторные пространства такие короткие строки «смазывают»: соседями
  оказываются `BAT54A` и `BAT54C`, а нужен ровно `BAT54`. Здесь нужен BM25.
* **Смысловой запрос.** «как снизить voiding на QFN» — ни одного общего слова
  с даташитом. Здесь работают только векторы.

OpenSearch держит оба поля в одном индексе и отвечает на гибридный запрос:
BM25 по `text/summary/part` (парт-номер усилен в 4 раза) плюс k-NN по
`vector`, результаты сливаются **Reciprocal Rank Fusion** — ранги, а не сырые
скоры, потому что у BM25 и косинуса нет общей шкалы. Плюс фильтры по
производителю, корпусу и секции — жёсткие, а не «похожие».

Свой анализатор в маппинге (`part_analyzer`: разделитель — всё, что не буква
и не цифра, плюс ngram 2–12) сделан ради того, чтобы `SOT-23-5` и `V(BR)CEO`
не рассыпались в мусор — это ровно то место, где стандартный анализатор
убивает поиск по маркировке.

Поднять узел на этой же машине:

```bash
sudo sysctl -w vm.max_map_count=262144          # один раз, до старта
docker compose -f tools/rag/opensearch-compose.yml up -d
curl http://localhost:9200                      # должен ответить

export SMD_OPENSEARCH_URL=http://localhost:9200
python3 tools/rag/pipeline.py --rebuild --backend opensearch --embed sentence-transformers
python3 tools/rag/serve.py --port 8000 --backend opensearch
```

Переменные: `SMD_OPENSEARCH_URL`, `SMD_OPENSEARCH_INDEX` (`smd-chunks`),
`SMD_OPENSEARCH_DIMS`, `SMD_OPENSEARCH_USER/PASS`, `--backend
auto|opensearch|sqlite`. **Если кластера нет, `auto` продолжает на SQLite** —
сайт не падает.

**Векторный канал работает и без OpenSearch.** Гибрид (BM25 + векторы)
умеет и SQLite-бэкенд — векторы там хранятся в отдельной таблице и ищутся
через numpy:

```bash
.venv/bin/pip install sentence-transformers
python3 tools/rag/pipeline.py --rebuild --embed sentence-transformers
```

OpenSearch нужен не для векторов как таковых, а для масштаба: на 300 тысячах
даташитов это ~15 млн чанков, и один процесс с numpy по ним уже не успевает.
До примерно миллиона чанков SQLite хватает.

Зависимость от `opensearch-py` не вводится намеренно: модуль говорит с кластером
по HTTP через urllib — так же, как `fetch_s3.py` подписывает запросы сам, без
boto3.

### Оркестрация

Чанкование — структурное, по заголовкам Markdown, через
`MarkdownElementNodeParser` из **LlamaIndex** (как вы и просили: не LangChain).
Схема пайплайна — обычный Python, ~200 строк; отдельный orchestration-слой ей
не нужен. Langflow — визуальная надстройка поверх LangChain; если нужен именно
он как прототипировщик, это отдельная развилка, см. ниже.

## Как это работает

**Поиск устойчив к ошибкам распознавания** — это ключевое отличие. Обычный поиск
по подстроке ломается там, где OCR ошибся всего в одном символе:

| Запрос | Что происходит |
|---|---|
| `A7` | оба кандидата: **BAV99** (92 %) и 1N4148W (86 %). Код `A7` у 1N4148W помечен как ненадёжный, поэтому BAV99 выше |
| `A7` + фильтр `SOD-123` | первым становится **1N4148W** — корпус снял неоднозначность |
| `7O2` | находится **2N7002**: замена `O`→`0` стоит 0.2, а не 1.0, и это трактуется как ошибка OCR |
| `1AM` | находится **MMBT3904**: `M` распознано как код партии и отсечено |
| `662K` | **XC6206P332MR** |

Оценка собирается из явных слагаемых, и каждое показывается пользователю в
`Match reasons`: точное совпадение, штраф за короткий код, бонус за совпадение
корпуса, надёжность конкретного кода в базе.

**OCR** не отправляет картинку в Tesseract «как есть». Кадр кадрируется,
бинаризуется порогом Оцу, прогоняется с инверсией (лазерная маркировка — это
светлый текст на тёмном компаунде, а движки ждут обратного) и с локальным
порогом против бликов. Затем каждый вариант распознавания прогоняется через
поиск, и результат показывается в виде «распознано → найдено в базе».

## Поиск по даташитам (RAG)

Второй движок: вместо «угадай по коду» — вопрос к своим PDF («какой у MMBT3904
максимальный ток коллектора?») с ответом-цитатой и ссылкой на страницу.

```bash
python3 -m venv .venv && .venv/bin/pip install -r tools/requirements.txt

python3 tools/rag/pipeline.py --corpus data/datasheets --rebuild   # собрать индекс
python3 tools/rag/serve.py --port 8000                             # сайт + API
```

Запросы из командной строки (без браузера):

```bash
python3 tools/rag/pipeline.py --query "collector current" --part MMBT3904
python3 tools/rag/pipeline.py --query "maximum input voltage" --part AMS1117-3.3
python3 tools/rag/pipeline.py --query "gate threshold" --section absolute_maximum_ratings
python3 tools/rag/pipeline.py --stats
```

HTTP API (тот же, что дёргает интерфейс):

| Метод | Что возвращает |
|---|---|
| `GET /api/health` | готов ли индекс + краткая статистика |
| `GET /api/stats` | счётчики: документы, чанки, таблицы, разделы |
| `GET /api/parts` | список деталей для фильтра |
| `GET /api/search?q=&part=&section=&k=` | passages с подсветкой совпадений |
| `GET /pdfs/<file>` | сам PDF (чтобы ссылка «Open PDF» работала) |
| `GET /api/cards?q=&pkg=&mfr=&limit=&offset=` | карточки: поиск + фильтры |
| `GET /api/card?part=` | одна карточка целиком |
| `GET /api/cards/stats` | счётчики и фасеты (корпуса, производители) |

### Как устроено

- **Парсер №1 — Docling (IBM)**, **`get_parser('auto')`** берёт его, если пакет
  установлен; иначе — pdfplumber. По ТЗ Docling основной, но его веса (~2 ГБ)
  в этой песочнице недоступны, поэтому реально отрабатывает pdfplumber, и
  пайплайн честно пишет, чем и почему парсил:

  ```
  Parser:      pdfplumber
               (skipped docling) — No module named 'docling'
  ```

  На своей машине: `pip install docling` — и Docling подхватится автоматически,
  без правок кода. Уточнения:

  - **Явный `--parser docling` не подменяется молча.** Если Docling не может
    работать, пайплайн падает с понятной ошибкой, а не парсит другим движком:
    доверять результату, полученному не тем парсером, нельзя.
  - **Docling не отдаёт таблицы по страницам**, а карточки строятся именно из
    таблиц. Поэтому Docling-режим гибридный: markdown для поиска от Docling,
    таблицы — от pdfplumber (офлайн, без весов). Иначе получились бы отличные
    чанки при пустых карточках.
- **Парсер №2 (vision-RAG для чертежей корпусов) не реализован**: веса VLM
  (Qwen2-VL, Llama-3.2-Vision) и Ollama из песочницы не скачиваются. Код к этому
  готов — чанк `package_dimensions` уже выделяется отдельно.
- **Оркестрация и чанкование — LlamaIndex**, не LangChain:
  `MarkdownElementNodeParser` режет по markdown-заголовкам, таблицы не
  разрываются. Разделы приводятся к каноничным именам: General Description /
  Features, Pin Configuration, Absolute Maximum Ratings, Package Dimensions…
- **Метаданные каждого чанка**: Part Number, Manufacturer, Package, раздел,
  страница, флаг «таблица». Это даёт жёсткий фильтр — `--part MMBT3904`
  отсекает всё, что не относится к детали, а не просто ранжирует.
- **Поиск гибридный**: BM25 (FTS5) всегда, плотные векторы — опционально;
  слияние списков по RRF (`1/(60+rank)`). Без векторов индекс всё равно
  рабочий, поэтому `--embed none` стоит по умолчанию.

Текущая статистика на демо-корпусе (13 PDF): **258 чанков, 63 таблицы**, 13
деталей, сборка ~6 с.

## Карточки компонентов (то, что видит пользователь)

Поиск по тексту отвечает на вопрос «где это написано?», но сайту нужны готовые
**карточки**: распиновка, предельные режимы, ключевые параметры, габариты.
Извлекатель `tools/rag/extract.py` собирает их из таблиц PDF правилами — без
LLM, поэтому 300 тысяч документов считаются процессором, а не бюджетом API.

```bash
python3 tools/rag/build_cards.py --corpus data/datasheets --jobs 8
python3 tools/rag/build_cards.py --stats          # что получилось
python3 tools/rag/build_cards.py --show MMBT3904  # одна карточка целиком
```

Что достаётся из таблиц:

| Таблица в PDF | Поле карточки |
|---|---|
| `Pin / Name / Function` | распиновка: 1 Base, 2 Emitter, 3 Collector |
| `Symbol / Parameter / Value / Unit` | предельные режимы (Vceo 40 В, Ic 200 мА) |
| `Symbol / Parameter / Conditions / Min / Typ / Max` | электрические характеристики |
| `Dimension / Min / Nom / Max` | габариты корпуса и шаг выводов |
| `Order code / Package / Marking` | коды заказа и маркировка |

Символы приводятся к каноническим именам (`V(BR)CEO`, `VCEO`, `V CE` →
`collector_emitter_voltage`), значения — к базовым единицам (200 мА → 0.2 А),
чтобы можно было фильтровать и сортировать. У каждого поля сохранён номер
страницы, и карточка показывает его: число всегда можно проверить по PDF.

Результат — `data/cards/cards.db` (источник истины, поиск по FTS5) плюс
статические шарды `data/cards/site/` — `brief/XX.json` для сетки и
`card/<PART>.json` для одной детали. Шарды позволяют выложить сайт на любой
статический хостинг вообще без API.

## 300 000 PDF на одной машине

Считать всё будем на одном компьютере — в вашем случае это Ubuntu, 16 ядер /
32 потока и 128 ГБ памяти. Кластер не нужен: разбор упирается в процессор, а
база одна, и записывает в неё ровно один процесс. Узкое место — не железо, а
то, что прогон длится часы, поэтому всё ниже — про то, чтобы эти часы можно
было прерывать, продолжать и не переделывать.

### 1. Сначала замерьте скорость на своих файлах

Универсального числа «PDF в секунду» не существует: двухстраничный диод и
сорокастраничный даташит — разница на порядок. Поэтому перед большим прогоном
запустите замер на **своём** корпусе:

```bash
python3 tools/rag/bench.py --corpus /mnt/datasheets --files 200 --jobs 8,16,24,32
```

Бенч берёт 200 файлов, причём десятку самых больших включает намеренно (иначе
проба из начала списка превратится в 200 диодов, и оценка будет врать в разы),
прогоняет их при каждом числе рабочих и печатает:

```
   8 workers:  38.20 s ·   5.24 PDF/s ·  22.1 MB/s · RSS peak   2100 MB · ok=200 failed=0
  16 workers:  21.40 s ·   9.35 PDF/s ·  39.5 MB/s · RSS peak   3900 MB · ok=200 failed=0
  24 workers:  15.10 s ·  13.25 PDF/s ·  55.9 MB/s · RSS peak   5800 MB · ok=200 failed=0
  32 workers:  14.80 s ·  13.51 PDF/s ·  57.0 MB/s · RSS peak   7600 MB · ok=200 failed=0

Extrapolated to 300 000 PDFs:
   06:17:20   with 32 workers
```

Дальше вся арифметика — из этой строки. 300 000 ÷ PDF/с = часы.

### 2. Сколько рабочих процессов

`pdfplumber` — чистый Python, задача често CPU-bound. На 32 потоках оптимум
обычно 24–32: после предела ядра начинают толкаться за памятью и диском, и
прирост исчезает (в примере выше 32 рабочих дают +2 % к 24). Ставить 64 не
имеет смысла, а вот `ulimit -n` поднять стоит — на 32 процессах открытых
файлов много.

### 3. Ночной прогон

```bash
python3 tools/rag/build_cards.py --corpus /mnt/datasheets --jobs 24 --no-shards
```

`--no-shards` важен: статические шарды — это по одному JSON-файлу на карточку,
300 тысяч мелких файлов. Сайт читает SQLite, шарды нужны только для
статического хостинга, и их лучше выгрузить один раз, когда база готова:

```bash
python3 tools/rag/build_cards.py --dump-shards
```

### 4. Прерывать можно в любой момент

Обработанные файлы запоминаются по SHA1: повторный запуск по той же папке
продолжает с того же места (`skipped`), ничего не пересчитывая. Коммит идёт
пачками по 25 файлов, но не реже раза в минуту — при сбое теряется минута
работы, а не ночь. Ctrl-C завершает текущую пачку и корректно выходит.

Один битый PDF не роняет прогон: он уходит в таблицу `failures` с текстом
ошибки, остальные считаются дальше.

### 5. Память и диск

| | Оценка на 300 000 карточек |
|---|---|
| `cards.db` | ≈ 6 КБ JSON на карточку, ~9 КБ с FTS5 и индексами → **3–5 ГБ** |
| WAL | до ~64 МБ между чекпоинтами (`wal_autocheckpoint`) |
| ОЗУ | каждый рабочий держит один PDF: 32 × самый большой файл |
| Время | из `bench.py`, обычно 6–20 часов |

Замерено на демо-корпусе: 200 PDF → 200 карточек, 9.4 с при 2 рабочих
(21 PDF/с), база 1.8 МБ, повторный прогон — 0.5 с (всё пропущено по SHA1).
На реальных даташитах карточки богаче, поэтому на диске закладывайте 3–5 ГБ.

128 ГБ более чем достаточно: даже если даташиты по 100 МБ, 32 рабочих займут
около 3–5 ГБ. Настройки SQLite уже выставлены под большой прогон: WAL,
256 МБ кэша, `mmap` 1 ГБ, `busy_timeout` 60 с, большой `wal_autocheckpoint`.
`SMD_SQLITE_SYNC=OFF` ускоряет запись, но переживает только сбой процесса, а
не обесточивание — включайте, если машина под ИБП:

```bash
SMD_SQLITE_SYNC=OFF python3 tools/rag/build_cards.py --corpus /mnt/datasheets --jobs 24 --no-shards
```

### 6. Прогон и сайт одновременно

Сайт читает ту же базу, что пишет прогон: WAL позволяет одному писателю и
скольким угодно читателям работать одновременно. Если днём пользуетесь сайтом,
запускайте прогон с меньшим числом рабочих (`--jobs 8`) — так интерфейс не
будет подтормаживать. Прогресс виден и в веб-интерфейсе (блок
«1 · Load your PDFs»), и в статусе задачи.

### 7. Поиск (RAG) считайте отдельно

300 тысяч даташитов — это около 15 млн чанков: на порядок больше, чем база
карточек. Карточки считайте первыми (именно они то, что видит пользователь), а
индекс поиска — потом и выборочно, благо `pipeline.py` умеет фильтровать по
производителю и секции. На таком объёме разумно вынести поиск в Meilisearch
или разложить FTS5-шарды по первой букве — `index_db.py` это допускает.

### 8. Если одной машины всё же не хватит

`--shard 1/4`, `--shard 2/4` … — каждый процесс берёт каждый четвёртый файл и
пишет в свой `cards.db`. Потом базы сливаются копированием строк: дубликаты по
`part` не страшны, `upsert` оставляет более полную карточку.

### 9. Юридически

Даташиты — чужая интеллектуальная собственность. Скачивать их пачками можно
только для себя; публичный сайт с раздачей PDF лучше строить на ссылках на
сайты производителей.

## Где взять PDF для базы

Качество базы определяется корпусом: если в PDF нет текстового слоя или
таблица распиновки — карточка будет пустой, сколько ни старайся извлекателем.
Поэтому корпус собирают не «откуда придётся», а по списку деталей.

### Правильный порядок

1. **Сначала список деталей, потом файлы.** Парт-номера, производители,
   корпуса — всё это есть в каталогах дистрибьюторов, и оттуда же берутся
   ссылки на даташиты. Список в CSV → пачка PDF.
2. **Качайте проверенно.** `tools/rag/fetch_datasheets.py` сам ставит паузы
   между запросами, повторяет при 5xx, проверяет, что пришёл именно PDF, не
   сохраняет дубли (по SHA1) и пишет `manifest.jsonl`, где по каждому файлу
   видно, откуда он и когда взят.

```bash
# parts.csv: part,manufacturer,package,url
python3 tools/rag/fetch_datasheets.py --list parts.csv --out data/datasheets --dry-run
python3 tools/rag/fetch_datasheets.py --list parts.csv --out data/datasheets --delay 1.0
```

Ссылку можно не указывать: если в строке есть производитель, URL строится по
его шаблону (TI, ST, Microchip, NXP, onsemi, Diodes, Vishay, ROHM — см.
`VENDOR_PATTERNS` в файле). Шаблоны — лучшее усилие: производители их меняют,
поэтому сначала `--dry-run`, а если что-то 404 — впишите реальный URL в CSV.

### Откуда брать список деталей

| Источник | Что даёт | Комментарий |
|---|---|---|
| **[jlcparts](https://yaqwsx.github.io/jlcparts/)** — открытый дамп каталога JLCPCB/LCSC | несколько миллионов **SMD**-позиций: парт-номер, производитель, корпус, ссылка на PDF | **Основной источник.** Скачивается целиком, без API и ключей — ровно то, что нужно для 300k |
| Сайты производителей (TI, ST, Microchip, NXP, onsemi, Diodes, Vishay, ROHM) | эталонные PDF | Качать по списку с паузами; URL строятся автоматически |
| Digi-Key, Mouser, TME (API) | точные данные по позиции, ссылка на PDF | Удобно закрывать дыры, но **условия Digi-Key прямо запрещают массовую выгрузку и построение базы из API** — используйте для поиска и уточнения, не как склад |
| Octopart / Nexar | агрегированный каталог | Бесплатный план — **~1000 деталей в месяц**, для 300 тысяч не годится |
| **Открытые библиотеки** | готовые пачки PDF | Например [uConfig](https://github.com/Robotips/uConfig) — оттуда взяты 7 даташитов в `data/datasheets` |

Агрегаторы вроде alldatasheet.com грешат сканами без текстового слоя и
устаревшими ревизиями; если берёте оттуда — прогоните корпус через
`build_cards.py` и посмотрите на долю карточек с распиновкой.

### Из каталога JLCPCB/LCSC — одной командой

```bash
# 1. скачайте cache.sqlite3 с https://yaqwsx.github.io/jlcparts/
#    (архив разбит на части: cat cache.z* cache.zip > all.zip && unzip all.zip)

# 2. превратите каталог в список деталей
python3 tools/rag/fetch_datasheets.py --from-jlcparts cache.sqlite3 \
        --to-csv parts.csv --basic-only --min-stock 100

# 3. посмотрите, что получится, и скачайте
python3 tools/rag/fetch_datasheets.py --list parts.csv --out data/datasheets --dry-run
python3 tools/rag/fetch_datasheets.py --list parts.csv --out data/datasheets --delay 1.0
```

`--basic-only` оставляет только basic/preferred (то, что ставят без доплаты),
`--min-stock` отсеивает позиции без склада, `--category` фильтрует по имени
категории (например `--category Transistors`). Экспортёр не верит в схему: он
смотрит `PRAGMA table_info` и ищет колонки по именам, поэтому переживёт
изменения формата — а если не найдёт, честно напечатает, какие колонки есть в
файле.

### Юридически

Даташиты — интеллектуальная собственность производителей. Скачивать их для
своей локальной базы — обычная практика; **выкладывать PDF на публичном сайте
нельзя** — ссылайтесь на страницу производителя. Именно поэтому в проекте
карточки (факты: распиновка, предельные режимы, габариты) отделены от файлов:
факты можно показывать, PDF — только по ссылке.

## Своя база данных

Встроенные 104 записи — демонстрационный набор. Рабочая база подключается так:

```bash
node tools/import_dataset.mjs markings.csv --merge
# → data/extra-parts.json
```

Затем в интерфейсе: **Import CSV / JSON**. Импортированные записи сохраняются
в `localStorage` вашего браузера.

Формат CSV (разделитель `,` или `;` определяется автоматически):

```
part,mfr,pkg,type,desc,v,i,pins,markings,conf,note
```

- `part`, `pkg` — обязательны;
- `markings` — несколько кодов через `|`;
- `conf` — `high` (код устойчив между производителями) / `med` / `low`
  (код конкретного завода, есть конфликты).

Подробности о формате и назначении полей — в `data/README.md`.

> **Маркировка SMD не стандартизована.** Один и тот же код у разных
> производителей означает разные детали. Любой результат нужно подтверждать
> по datasheet перед заменой компонента.

## Тесты

```bash
node tools/test-matcher.js        # ядро поиска: 30 проверок
npm install && npm test           # + smoke-тест интерфейса в jsdom: 43 проверки
python3 tools/test_rag.py         # RAG целиком (парсинг, индекс, API): 26 проверок
python3 tools/test_cards.py       # извлечение карточек, база и шарды: 40 проверок
python3 tools/test_ingest.py      # веб-парсер: папка, загрузка, отмена: 23 проверки
python3 tools/rag/bench.py --corpus /mnt/datasheets   # замер PDF/с на вашей машине
python3 tools/rag/doctor.py                 # диагноз: что стоит и что отвечает
python3 tools/rag/fetch_datasheets.py --list parts.csv --dry-run  # скачать корпус
```

`tools/test_rag.py` сам генерирует временный корпус PDF, собирает индекс,
поднимает HTTP-обработчик и проверяет ответы — внешних сервисов не нужно.
`tools/test_ingest.py` запускает настоящий сервер на свободном порту и работает
с ним так же, как браузер: отправляет путь к папке, грузит файлы multipart'ом,
опрашивает прогресс и отменяет прогон.

Если что-то не работает, начните с `python3 tools/rag/doctor.py`: он печатает
железо, установленные пакеты, доступность OpenSearch, содержимое баз, последние
сбои разбора и состояние сайта. Вывод можно целиком прислать в чат.

## Windows

Проект кроссплатформенный, но несколько вещей на Windows отличаются:

* **Кодировка.** PowerShell и cmd по умолчанию отдают cp1251/cp866, из-за чего
  °, µ и → в выводе превращаются в кракозябры. Все консольные инструменты
  сами переключают stdout/stderr на UTF-8 (`tools/rag/cli.py`), так что
  `PYTHONIOENCODING=utf-8` больше не нужен.
* **OpenSearch.** Без Docker его не поднять. Варианты: Docker Desktop, WSL2
  (`wsl --install`, дальше всё как на Ubuntu) или просто работать на SQLite —
  включая векторный канал, см. выше.
* **Запуск сайта.** Обычно из того же терминала:
  `.venv\Scripts\python tools\rag\serve.py --port 8000 --jobs 8`.
  Через `Start-Process` тоже работает, но логи тогда не видны — для отладки
  запускайте в обычном окне.
* **Пути.** В поле «Folder path» на сайте годится и `C:\Datasheets`, и
  `C:/Datasheets`. Слэши в любую сторону — путь всё равно дойдёт.
* **Производительность.** Пул процессов на Windows стартует медленнее, чем
  fork на Linux, поэтому на больших корпусах выигрыш от `--jobs 32` меньше,
  чем на Ubuntu. Замеряйте `bench.py` на своей машине.

## Ограничения

- База — seed-набор, а не авторитетный справочник.
- OCR-движок (tesseract.js) подгружается с CDN при первом использовании;
  для работы без интернета положите его рядом.
- Тестировалось в Node 22 и jsdom; на реальных макрофото камеры предобработка
  не проверялась.
- **Docling не отработал**: пакет рассчитан на машины с доступом к весам модели;
  в песочнице они заблокированы, срабатывает fallback на pdfplumber. На своей
  машине `pip install docling` — и парсер подхватится автоматически.
- **Vision-парсер для чертежей корпусов отсутствует** по той же причине.
- **S3 из песочницы недоступен** (все эндпоинты блокируются), поэтому
  `tools/rag/fetch_s3.py` рассчитан на запуск у вас: креды берутся из переменных
  окружения, boto3 не нужен.
