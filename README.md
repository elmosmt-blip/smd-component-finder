# smd-component-finder

Инструмент идентификации SMD-компонентов по маркировке, номеру детали или снимку с камеры.

Два движка: **поиск по маркировке** (нечёткий, полностью в браузере) и **поиск по
даташитам** (RAG по локальной библиотеке PDF, поднимается одним скриптом).
Всё локально: ничего не уходит на сервер.

> **Интерфейс — на английском** (так удобнее для общедоступного инструмента);
> этот README и комментарии в Python-инструментах — на русском.

Репозиторий появился как результат разбора эталонного инструмента
[smtinsider.com/finder](https://www.smtinsider.com/finder). Разбор — в **[ANALYSIS.md](ANALYSIS.md)**:
что там сделано хорошо, какие узкие места и что именно переделано здесь.

## Быстрый старт

Открыть локально (без сборки и зависимостей):

```bash
# статический сервер без RAG (поиск по маркировке работает, панель даташитов — нет)
python3 -m http.server 8000

# полный вариант: сайт + /api/* на одном origin
python3 tools/rag/serve.py --port 8000
# затем http://localhost:8000
```

Сборка не требуется. Поиск по маркировке работает и при открытии `index.html`
напрямую с диска, а вот камера и `/api/*` потребуют `https://` или `localhost` —
это ограничение браузера, а не кода.

## Как это работает

**Поиск устойчив к ошибкам распознавания** — это ключевое отличие. Обычный поиск
по подстроке ломается там, где OCR ошибся всего в одном символе:

| Запрос | Что происходит |
|---|---|
| `A7` | оба кандидата: **BAV99** (92 %) и 1N4148W (86 %). Код `A7` у 1N4148W помечен как ненадёжный, поэтому BAV99 выше |
| `A7` + фильтр `SOD-123` | первым становится **1N4148W** — корпус снял неоднозначность |
| `7O2` | находится **2N7002**: замена `O`→`0` стоит 0.2, а не 1.0, и это трактуется как ошибка OCR |
| `1AM` | находится **MMBT3904**: `M` распознано как код партии и отсечено |
| `662K` | **XC6206P332MR** |

Оценка собирается из явных слагаемых, и каждое показывается пользователю в
`Match reasons`: точное совпадение, штраф за короткий код, бонус за совпадение
корпуса, надёжность конкретного кода в базе.

**OCR** не отправляет картинку в Tesseract «как есть». Кадр кадрируется,
бинаризуется порогом Оцу, прогоняется с инверсией (лазерная маркировка — это
светлый текст на тёмном компаунде, а движки ждут обратного) и с локальным
порогом против бликов. Затем каждый вариант распознавания прогоняется через
поиск, и результат показывается в виде «распознано → найдено в базе».

## Поиск по даташитам (RAG)

Второй движок: вместо «угадай по коду» — вопрос к своим PDF («какой у MMBT3904
максимальный ток коллектора?») с ответом-цитатой и ссылкой на страницу.

```bash
python3 -m venv .venv && .venv/bin/pip install -r tools/requirements.txt

python3 tools/rag/pipeline.py --corpus data/datasheets --rebuild   # собрать индекс
python3 tools/rag/serve.py --port 8000                             # сайт + API
```

Запросы из командной строки (без браузера):

```bash
python3 tools/rag/pipeline.py --query "collector current" --part MMBT3904
python3 tools/rag/pipeline.py --query "maximum input voltage" --part AMS1117-3.3
python3 tools/rag/pipeline.py --query "gate threshold" --section absolute_maximum_ratings
python3 tools/rag/pipeline.py --stats
```

HTTP API (тот же, что дёргает интерфейс):

| Метод | Что возвращает |
|---|---|
| `GET /api/health` | готов ли индекс + краткая статистика |
| `GET /api/stats` | счётчики: документы, чанки, таблицы, разделы |
| `GET /api/parts` | список деталей для фильтра |
| `GET /api/search?q=&part=&section=&k=` | passages с подсветкой совпадений |
| `GET /pdfs/<file>` | сам PDF (чтобы ссылка «Open PDF» работала) |
| `GET /api/cards?q=&pkg=&mfr=&limit=&offset=` | карточки: поиск + фильтры |
| `GET /api/card?part=` | одна карточка целиком |
| `GET /api/cards/stats` | счётчики и фасеты (корпуса, производители) |

### Как устроено

- **Парсер №1 — Docling (IBM)**, **`get_parser('auto')`** берёт его, если пакет
  установлен; иначе — pdfplumber. По ТЗ Docling основной, но его веса (~2 ГБ)
  в этой песочнице недоступны, поэтому реально отрабатывает pdfplumber, и
  пайплайн честно пишет, чем и почему парсил:

  ```
  Parser:      pdfplumber
               (skipped docling) — No module named 'docling'
  ```

  На своей машине: `pip install docling` — и Docling подхватится автоматически,
  без правок кода. Уточнения:

  - **Явный `--parser docling` не подменяется молча.** Если Docling не может
    работать, пайплайн падает с понятной ошибкой, а не парсит другим движком:
    доверять результату, полученному не тем парсером, нельзя.
  - **Docling не отдаёт таблицы по страницам**, а карточки строятся именно из
    таблиц. Поэтому Docling-режим гибридный: markdown для поиска от Docling,
    таблицы — от pdfplumber (офлайн, без весов). Иначе получились бы отличные
    чанки при пустых карточках.
- **Парсер №2 (vision-RAG для чертежей корпусов) не реализован**: веса VLM
  (Qwen2-VL, Llama-3.2-Vision) и Ollama из песочницы не скачиваются. Код к этому
  готов — чанк `package_dimensions` уже выделяется отдельно.
- **Оркестрация и чанкование — LlamaIndex**, не LangChain:
  `MarkdownElementNodeParser` режет по markdown-заголовкам, таблицы не
  разрываются. Разделы приводятся к каноничным именам: General Description /
  Features, Pin Configuration, Absolute Maximum Ratings, Package Dimensions…
- **Метаданные каждого чанка**: Part Number, Manufacturer, Package, раздел,
  страница, флаг «таблица». Это даёт жёсткий фильтр — `--part MMBT3904`
  отсекает всё, что не относится к детали, а не просто ранжирует.
- **Поиск гибридный**: BM25 (FTS5) всегда, плотные векторы — опционально;
  слияние списков по RRF (`1/(60+rank)`). Без векторов индекс всё равно
  рабочий, поэтому `--embed none` стоит по умолчанию.

Текущая статистика на демо-корпусе (13 PDF): **258 чанков, 63 таблицы**, 13
деталей, сборка ~6 с.

## Карточки компонентов (то, что видит пользователь)

Поиск по тексту отвечает на вопрос «где это написано?», но сайту нужны готовые
**карточки**: распиновка, предельные режимы, ключевые параметры, габариты.
Извлекатель `tools/rag/extract.py` собирает их из таблиц PDF правилами — без
LLM, поэтому 300 тысяч документов считаются процессором, а не бюджетом API.

```bash
python3 tools/rag/build_cards.py --corpus data/datasheets --jobs 8
python3 tools/rag/build_cards.py --stats          # что получилось
python3 tools/rag/build_cards.py --show MMBT3904  # одна карточка целиком
```

Что достаётся из таблиц:

| Таблица в PDF | Поле карточки |
|---|---|
| `Pin / Name / Function` | распиновка: 1 Base, 2 Emitter, 3 Collector |
| `Symbol / Parameter / Value / Unit` | предельные режимы (Vceo 40 В, Ic 200 мА) |
| `Symbol / Parameter / Conditions / Min / Typ / Max` | электрические характеристики |
| `Dimension / Min / Nom / Max` | габариты корпуса и шаг выводов |
| `Order code / Package / Marking` | коды заказа и маркировка |

Символы приводятся к каноническим именам (`V(BR)CEO`, `VCEO`, `V CE` →
`collector_emitter_voltage`), значения — к базовым единицам (200 мА → 0.2 А),
чтобы можно было фильтровать и сортировать. У каждого поля сохранён номер
страницы, и карточка показывает его: число всегда можно проверить по PDF.

Результат — `data/cards/cards.db` (источник истины, поиск по FTS5) плюс
статические шарды `data/cards/site/` — `brief/XX.json` для сетки и
`card/<PART>.json` для одной детали. Шарды позволяют выложить сайт на любой
статический хостинг вообще без API.

## 300 000 PDF: как это делать

Такая библиотека обрабатывается не за один присест, поэтому сборщик сразу
рассчитан на долгую работу.

**1. Оцените скорость на своей машине.** Реальные даташиты — 10–50 страниц, и
это решающий фактор:

```bash
python3 tools/rag/build_cards.py --limit 200 --jobs 8 --out /tmp/probe
```

Сборщик печатает PDF/с. Ориентир: ~2 PDF/с на ядро на коротких документах,
0.2–0.5 PDF/с на ядро на даташитах по 20–40 страниц. Дальше арифметика простая:
300 000 ÷ (0.3 × 16 ядер) ≈ 17 часов. Это ночь на одном 16-ядерном сервере, а
не «быстрый скрипт».

**2. Запускайте в несколько машин.** `--shard 1/4`, `--shard 2/4` … — каждый
процесс берёт каждый четвёртый файл. Шарды складываются в свои `cards.db`;
дальше их можно слить копированием строк (дубликаты по `part` не страшны —
`upsert` оставляет более полную карточку).

**3. Прерывание бесплатно.** Обработанные файлы запоминаются по SHA1, поэтому
повторный запуск продолжает с того же места. Ctrl-C завершает текущую пачку,
коммитит и выходит — ничего не теряется.

**4. Один плохой PDF не роняет прогон.** Ошибки пишутся в таблицу `failures` с
текстом исключения; в конце видно, сколько документов не разобралось и почему.

**5. Сначала текст, потом картинки.** Текстовый слой (таблицы) даёт 90 % полей.
Чертежи корпусов и распиновку-картинку извлекает только vision-модель, это
дорого и в песочнице недоступно; если понадобится — чанк `package_dimensions`
уже выделен отдельно, к нему и цеплять.

**6. Держите карточки и поиск分开.** На 300 тысячах частей индекс поиска
(15 млн чанков) и база карточек (300 тысяч строк) — разные вещи по размеру на
порядок. Карточки маленькие, живут в SQLite и шардах; для поиска на таком
объёме разумно вынести FTS5-шарды по первой букве или поставить Meilisearch —
`index_db.py` умеет и то, и другое через `--part/--section` фильтры.

**7. Юридически.** Даташиты — чужая интеллектуальная собственность. Скачивать
их пачками можно только для себя; публичный сайт с раздачей PDF лучше
строить на ссылках на сайты производителей.

## Своя база данных

Встроенные 104 записи — демонстрационный набор. Рабочая база подключается так:

```bash
node tools/import_dataset.mjs markings.csv --merge
# → data/extra-parts.json
```

Затем в интерфейсе: **Import CSV / JSON**. Импортированные записи сохраняются
в `localStorage` вашего браузера.

Формат CSV (разделитель `,` или `;` определяется автоматически):

```
part,mfr,pkg,type,desc,v,i,pins,markings,conf,note
```

- `part`, `pkg` — обязательны;
- `markings` — несколько кодов через `|`;
- `conf` — `high` (код устойчив между производителями) / `med` / `low`
  (код конкретного завода, есть конфликты).

Подробности о формате и назначении полей — в `data/README.md`.

> **Маркировка SMD не стандартизована.** Один и тот же код у разных
> производителей означает разные детали. Любой результат нужно подтверждать
> по datasheet перед заменой компонента.

## Ограничения

- База — seed-набор, а не авторитетный справочник.
- OCR-движок (tesseract.js) подгружается с CDN при первом использовании;
  для работы без интернета положите его рядом.
- Тестировалось в Node 22 и jsdom; на реальных макрофото камеры предобработка
  не проверялась.
- **Docling не отработал**: пакет рассчитан на машины с доступом к весам модели;
  в песочнице они заблокированы, срабатывает fallback на pdfplumber. На своей
  машине `pip install docling` — и парсер подхватится автоматически.
- **Vision-парсер для чертежей корпусов отсутствует** по той же причине.
- **S3 из песочницы недоступен** (все эндпоинты блокируются), поэтому
  `tools/rag/fetch_s3.py` рассчитан на запуск у вас: креды берутся из переменных
  окружения, boto3 не нужен.
